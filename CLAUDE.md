# GFSupport — правила, которые не выводятся из кода

Прочитать до первой правки. Каждый пункт здесь — оплаченный шишками факт.

## База и время

- **Два мира таймстампов.** В `support_*` — наивный `timestamp` с UTC:
  для Ташкента обязательна двойная конверсия
  `AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Tashkent'`. В `sales_*` —
  `timestamptz`: там конверсия ОДИНАРНАЯ (`AT TIME ZONE 'Asia/Tashkent'`),
  двойная сдвигает время на −10 часов. Проверять тип колонки
  в DATABASE_SCHEMA.md, не переносить привычку между мирами.
- **Дорога до базы ≈ 190 мс** (функции и база во Франкфурте, но edge-часть
  дальше). Несколько последовательных запросов = секунды. Собирать
  в `sql.transaction` пачкой.
- **DDL живёт в обработчиках** (`CREATE TABLE IF NOT EXISTS`), смягчено
  `ensureOnce` — один прогон на холодный старт. Новые таблицы заводить
  тем же паттерном, а не отдельной миграцией.
- **Смена `SCHEMA_VERSION` в `_lib/sales-schema.ts`** гоняет весь DDL
  продаж. Применять миграцию до пуша; сиды — только пачками.
- **`sales_leads.updated_at` — наивный `timestamp`**, в отличие от остальных
  `sales_*` (timestamptz). Сравнивать с timestamptz можно (сессия базы в UTC),
  но конверсия для Ташкента у него — как у `support_*`, двойная.
- **Справочник схемы** генерируется: `node scripts/db-schema.mjs`
  → `DATABASE_SCHEMA.md`. Руками не править, после миграций перегенерировать.
- **`n_live_tup` врёт — это оценка планировщика, а не счёт строк.** Проверка
  08.09.2026: «пустых» таблиц по оценке 69, по настоящему `count(*)` — 53.
  Соврала на 16 таблицах, среди них `support_case_activity` (922 строки),
  `support_conversation_sessions` (466), `support_docs` (117), `crm_calls`,
  `support_super_admins`. Две из них уже стояли в списке на снос. Ничего
  не удалять и не считать пустым без `SELECT count(*)` по каждой таблице.
- **26 таблиц в CamelCase** (`Deal`, `Lead`, `Contract`, `Invoice`, `Product`…)
  — заброшенная модель ранней версии CRM: строк нет, кода нет. Соседние
  `User`, `Role`, `Currency`, `Territory`, `Pipeline`, `PipelineStage`,
  `SalesRep` из того же слоя — с сидовыми строками. Готовый снос лежит
  в `scripts/drop-dead-tables.mjs` (по умолчанию проверяет и сохраняет
  структуру, флаг `--dry` — только показать). Не запускался.

## Драйвер neon

- **Обратные кавычки внутри `` sql`...` `` ломают template literal** —
  даже в SQL-комментарии. Симптом: невнятный TS1005 при сборке.
- **Обратные слеши в строках запросов съедаются** (cooked strings).
  Регулярки в SQL — без `\`: писать `'[^0-9]'`, а не `'\d'`;
  значения передавать параметром, не склейкой.

## Смысл данных

- **«Клиенты» в аналитике = покупатели Delever**, не клиенты GFSupport.
  Система single-tenant под Delever, слово переопределено.
- **Кейс = тикет, канал = разговор.** FRT считается по тикету
  (`first_response_at − first_message_at`), канон в `_metrics/frtShared.ts`.
- **`resolved` остаётся на доске до конца дня** (Ташкент) и не входит
  в `ARCHIVE_STATUSES`. Закрывает ночной крон `archive-resolved` (00:15).
- **Даты в UI — всегда Asia/Tashkent** через `shared/lib/time.ts`,
  независимо от локали смотрящего: команда распределена.
- **Дубли агентов** сшиваются через `merged_into` (Насиба, два Аслиддина,
  два Хасана) — атрибуцию считать по канонической записи.

## Доступ

- **Ключ входа — не идентификатор сотрудника.** Идентификаторы (`agent_…`)
  система показывает в обычных ответах: владелец лида, ответственный, список
  команды. Пока токеном был идентификатор, любой сотрудник мог работать под
  чужой учётной записью. Сессии живут в `support_sessions`, в базе лежит
  отпечаток SHA-256, срок 30 дней со скользящим продлением, выход гасит сессию.
- **Неопознанный токен = гость.** Раньше `extractAgentContext` возвращал сам
  токен как `agentId`, и строка `Bearer agent_что_угодно` проходила проверку
  `if (!ctx.agentId)` во всех обработчиках — CRM читалась без учётной записи.
  Ошибка базы тоже выдавала доступ. Обе ветки теперь возвращают гостя.
- **Старые токены принимаются, пока `LEGACY_AGENT_TOKENS` не равен `off`.**
  Клиент меняет старый токен на сессию сам при первом открытии
  (`POST /agents/session {action:'upgrade'}`). После переезда команды
  переменную выставить в `off`.
- **`admin/sa-login.ts` до сих пор отдаёт `sa.id` как токен.** Идентификаторы
  супер-админов в обычных ответах не светятся, поэтому дыра уже, но правило
  то же — переводить на сессии.
- **Вход проверяет `middleware.ts`, а не каждый обработчик.** Аудит 08.09.2026:
  из ~250 обработчиков личность проверяли около двух пятых, остальные считали
  авторизацией наличие строки `Bearer ` либо не проверяли ничего. Список
  сотрудников, каналы, настройки и код привязки WhatsApp отдавались без входа,
  `POST /agents` заводил администратора любому желающему. Заслон стоит перед
  всеми путями `/api/support/*`; открыты только вебхуки, публичные страницы
  по токену, приём заявок, картинки и форма входа. Расписания — по `CRON_SECRET`.
  **Новый публичный адрес добавлять в `PUBLIC` осознанно**, а свою проверку
  в обработчике не убирать: это второй рубеж.
- **Отключение сотрудника закрывает вход.** `COALESCE(is_active, true)` в трёх
  местах опознания плюс гашение сессий при деактивации. Раньше увольнение
  меняло только статус, а ключ продолжал работать.
- **Осталось незакрытым** (требует решения владельца): телеграм-вебхуки без
  `secret_token` (подделываются), пароли под SHA-256 с общей солью и
  самодельный 32-битный хеш в `auth/register.ts`, открытый редирект
  в `broadcast/track.ts`, `media/proxy.ts` без белого списка доменов,
  `LEGACY_AGENT_TOKENS` ещё `on`.

## Интеграции

- **Три Telegram-бота, не путать токены:** `TELEGRAM_BOT_TOKEN` — ингест
  сообщений (@delever_sales_bot, сидит в ресторанных чатах),
  `PLATFORM_BOT_TOKEN` — только регистрация (@gfsupport_robot),
  `SALES_BOT_TOKEN` — продажи.
- **Директ Instagram отдаётся только одному приложению.** Подключить
  директ во втором = молча отобрать поток у первого.
- **Все объекты Meta ходят в один вебхук** (`webhook/meta-leads.ts`) —
  намеренно: разные адреса уже приводили к «подписка есть, обработчика нет».
- **WhatsApp шлёт LID вместо телефона** у части пользователей. Опознание —
  по последним 9 цифрам через `support_agents.phone` и по роли.
- **Amo: «fetched=N, deferred=N, created=0»** = синхронизация сломана
  (у неразобранной заявки вложенная сделка пуста). Курсор и живость —
  в `sales_amo_last_run`.
- **Вебхук OnlinePBX** подписан `sha256(api_key)`: смена ключа АТС
  означает смену URL вебхука.
- **Обратная петля Meta** (`cron/meta-feedback` + `_lib/meta-capi.ts`):
  события по фактам сделки (квалификация/встреча/оплата) → Conversions API.
  Включается из UI: настройки → интеграция Meta → «Обратная петля рекламы»
  (выбор пикселя кнопкой; право ads_read запрашивается ТОЛЬКО оттуда,
  режим `scopes=ads`, — дефолтный OAuth-диалог не менять, пока идёт
  App Review). Токен: capi_token (ручной) → user_token (OAuth) →
  page_token; env META_DATASET_ID/META_CAPI_TOKEN — последний фолбэк.
  Первый прогон помечает старые факты как baseline и НЕ шлёт их задним
  числом. Лог — `sales_meta_events`.
- **Google Календарь: «Ошибка 403: access_denied» у коллег** — это не наш
  код (он 403 не отдаёт), а режим Testing OAuth-приложения в Google Cloud:
  согласие могут дать только адреса из Test users. Лечится там: добавить
  людей или переключить приложение на Internal для домена.
- **Примечания Amo** едут в `sales_activities` кроном `cron/amo-notes`
  (по 25 сделок за проход, каждую один раз — отметка в
  `sales_amo_notes_state`, дедуп по `message_id = amo_note_<id>`).
- **Кроны** защищены общим `assertCron` (`CRON_SECRET` задан в проде,
  user-agent не подделывается).

## Сборка и код

- **`api/` проверяется отдельным tsconfig.** После правок в `api/`
  обязательно `npm run typecheck:api` — фронтовая сборка эти ошибки не видит.
- **Тесты гоняются в сборке** (`npm test` → vitest, входит в `npm run build`):
  упавшая проверка останавливает выкладку. Покрыты места, где ошибка молчит
  и стоит дорого: подбор заведения на картах (`_lib/places-match.ts`), разбор
  телефонов, ключ склейки дублей, сборка договора и отпечаток ключа входа.
  Случаи в тестах — с боевых карточек, а не выдуманные; при новой поломке
  сначала добавляется случай, потом правка.
- **В `support_channels` нет колонок `assigned_to` и `tags`**, хотя
  по смыслу их там ждёшь.
- **UI на русском**, абсолютные даты — ташкентские.
- **UI-изменения показывать макетом до пуша** — таково правило проекта.
- **Каждый деплой с исправлениями — запись в `api/support/_lib/release-notes.ts`**
  (первой в списке, новая `version`). Крон `cron/release-notes` раз в 10 минут
  сам разошлёт её сейлзам в систему и в Telegram; страница — «Что нового».
  Пишется языком команды: что было не так → что теперь → где смотреть.
